DDL Commands & Schema Design

Aim: To understand and apply Data Definition Language (DDL) commands — CREATE, ALTER, DROP, TRUNCATE — for designing and modifying a database schema with constraints.

What is DDL?

Data Definition Language (DDL) consists of SQL commands that define, modify, or remove the structure (schema) of database objects. DDL does not deal with actual data rows — it defines the blueprint of your database.

Core DDL Commands

  • CREATE — Creates a new database, table, view, or index
  • ALTER — Modifies an existing table (add / drop / modify columns, add constraints)
  • DROP — Permanently deletes a table along with all its data and structure
  • TRUNCATE — Deletes all rows in a table but keeps the table structure
  • RENAME — Renames a table or column

Column Constraints

  • PRIMARY KEY — Uniquely identifies each row; cannot be NULL
  • NOT NULL — The column must always have a value
  • UNIQUE — All values in the column must be distinct
  • CHECK — Value must satisfy a specified condition (e.g., age >= 18)
  • DEFAULT — A default value is inserted automatically when none is provided
  • FOREIGN KEY — Links to a PRIMARY KEY in another table to enforce referential integrity

Important: DDL vs DML

DDL commands (CREATE, DROP, TRUNCATE) auto-commit — changes are permanent immediately and cannot be rolled back. DML commands (INSERT, UPDATE, DELETE) can be wrapped in transactions and rolled back. This distinction is critical for database safety.

CREATE TABLE

-- Create a Students table with various constraints
CREATE TABLE Students (
    student_id   INT           PRIMARY KEY,
    name         VARCHAR(50)   NOT NULL,
    email        VARCHAR(100)  UNIQUE,
    age          INT           CHECK(age >= 16),
    dept         VARCHAR(30)   DEFAULT 'CS',
    joined_on    DATE
);

ALTER TABLE

-- Add a new column
ALTER TABLE Students ADD phone VARCHAR(15);

-- Modify a column's data type
ALTER TABLE Students MODIFY name VARCHAR(80) NOT NULL;

-- Drop a column
ALTER TABLE Students DROP COLUMN phone;

-- Add a foreign key constraint
ALTER TABLE Students
  ADD CONSTRAINT fk_dept
  FOREIGN KEY (dept_id) REFERENCES Department(dept_id);

DROP vs TRUNCATE

-- DROP: removes table definition + all data (irreversible)
DROP TABLE Students;

-- TRUNCATE: removes all rows, keeps table structure
TRUNCATE TABLE Students;

-- Difference at a glance:
-- DROP TABLE  → table no longer exists
-- TRUNCATE    → empty table still exists
-- DELETE      → removes rows (can use WHERE), is DML

DML Commands & SQL Queries

Aim: To learn and practice Data Manipulation Language (DML) commands — INSERT, UPDATE, DELETE, SELECT — and advanced clauses (WHERE, GROUP BY, HAVING, ORDER BY) on a live database table.

What is DML?

Data Manipulation Language (DML) commands operate on the actual data rows inside tables. Unlike DDL, DML operations can be wrapped inside transactions and rolled back if needed.

Core DML Commands

  • INSERT — Adds one or more new rows to a table
  • UPDATE — Modifies values in existing rows (always use WHERE or all rows change!)
  • DELETE — Removes rows from a table (always use WHERE or all rows are deleted!)
  • SELECT — Retrieves data from one or more tables (technically DQL, but covered here)

SELECT Clauses

  • WHERE — Filter rows before any grouping (e.g., WHERE age > 20)
  • ORDER BY — Sort results ascending (ASC) or descending (DESC)
  • GROUP BY — Collapse rows sharing the same column value into groups
  • HAVING — Filter groups after GROUP BY (like WHERE but for groups)
  • DISTINCT — Eliminate duplicate result rows
  • LIMIT — Return only the first N rows
  • Aggregate functions: COUNT(), SUM(), AVG(), MAX(), MIN()

INSERT

-- Insert a single row
INSERT INTO Students (student_id, name, age, dept)
VALUES (1, 'Alice', 20, 'CS');

-- Insert multiple rows at once
INSERT INTO Students VALUES
  (2, 'Bob',   19, 'IT'),
  (3, 'Carol', 21, 'CS'),
  (4, 'David', 22, 'ECE');

SELECT with Clauses

-- Get all rows and columns
SELECT * FROM Students;

-- Filter by condition and sort
SELECT name, age FROM Students
WHERE dept = 'CS' AND age >= 20
ORDER BY age DESC;

-- Count students per department
SELECT dept, COUNT(*) AS total
FROM Students
GROUP BY dept
HAVING COUNT(*) > 1
ORDER BY total DESC;

UPDATE & DELETE

-- Update a specific row (always use WHERE!)
UPDATE Students
SET dept = 'ECE', age = 23
WHERE student_id = 2;

-- Delete rows matching a condition
DELETE FROM Students
WHERE dept = 'ECE';

Normalization (1NF → 3NF)

Aim: To understand database normalization — transforming an unnormalized relation through 1NF, 2NF, and 3NF by identifying and eliminating functional dependencies, partial dependencies, and transitive dependencies.

What is Normalization?

Normalization is the process of organizing a database to reduce data redundancy and prevent anomalies. It restructures large tables into smaller, well-organized related tables using a series of rules called Normal Forms.

The Three Anomalies (Problems Without Normalization)

  • Insertion Anomaly: Cannot add a new record without supplying unrelated data
  • Update Anomaly: Changing one value requires updating multiple rows — inconsistency risk
  • Deletion Anomaly: Deleting one row accidentally removes other important information

Normal Forms — Quick Reference

  • UNF (Unnormalized): Raw data — multi-valued cells, no clear primary key
  • 1NF: Every cell is atomic (one value only); a primary key is defined
  • 2NF: 1NF + no partial dependency (non-key attributes must depend on the full composite key, not just part of it)
  • 3NF: 2NF + no transitive dependency (non-key attributes must depend only on the primary key, not on other non-key attributes)

Functional Dependency (FD)

Written as A → B ("A determines B"). If you know the value of A, you can always find exactly one value of B. Example: student_id → student_name. The Determinant (A) functionally determines the Dependent (B).

Transactions & ACID Properties

Aim: To understand database transactions, implement COMMIT and ROLLBACK commands, and demonstrate all four ACID properties (Atomicity, Consistency, Isolation, Durability) through an interactive bank transfer simulation.

What is a Transaction?

A transaction is a logical unit of work made up of one or more SQL operations that must be treated as a single whole. Either all operations succeed (COMMIT), or all are undone (ROLLBACK). Classic example: transferring money between bank accounts requires two UPDATEs — both must succeed or neither should.

Transaction Control Commands

  • BEGIN / START TRANSACTION — Marks the start of a new transaction
  • COMMIT — Permanently saves all changes made in the current transaction to disk
  • ROLLBACK — Undoes all changes since the last COMMIT or BEGIN
  • SAVEPOINT name — Creates a named intermediate checkpoint within a transaction
  • ROLLBACK TO name — Rolls back only to the specified SAVEPOINT (partial undo)
  • RELEASE SAVEPOINT name — Removes a savepoint (keeps the changes)

ACID Properties

  • Atomicity: All operations succeed or none do — the transaction is indivisible
  • Consistency: The database moves from one valid state to another — no constraints are violated
  • Isolation: Concurrent transactions do not see each other's intermediate uncommitted changes
  • Durability: After COMMIT, data is permanently written to disk — survives crashes

ACID Properties — Click Each Card to Expand

A
Atomicity
Bank transfer: ₹1000 leaves Account A AND arrives in Account B — or neither update happens. You cannot have half a transaction. If the system fails between the two steps, ROLLBACK restores both accounts to their original values.
C
Consistency
Before and after every transaction, all database rules — NOT NULL, FOREIGN KEY, CHECK constraints, triggers — must be satisfied. A transaction that would leave the database in an invalid state is automatically aborted.
I
Isolation
Two simultaneous transactions cannot see each other's uncommitted intermediate state. Isolation levels (READ UNCOMMITTED → SERIALIZABLE) control how strictly this is enforced. This prevents dirty reads, non-repeatable reads, and phantom reads.
D
Durability
Once a transaction is committed, its effects are permanent — even if the server crashes immediately after. The database engine uses a Write-Ahead Log (WAL) to replay all committed transactions on recovery, ensuring no committed data is ever lost.

Transaction SQL Reference

START TRANSACTION;
  UPDATE Account SET balance = balance - 1000 WHERE id = 'A';
  SAVEPOINT after_debit;
  UPDATE Account SET balance = balance + 1000 WHERE id = 'B';

  -- If credit fails, undo only the credit step:
  ROLLBACK TO after_debit;

  -- OR save everything permanently:
COMMIT;

Indexing & Query Optimization

Aim: To understand database indexing — how indexes are structured (B-Tree), how they accelerate queries, the different types of indexes, and when they should or should not be used.

What is a Database Index?

An index is a separate data structure that stores column values in sorted order with pointers to the original table rows. It works like the index at the back of a textbook — instead of scanning every page, you jump directly to the right location. Without an index, the database must scan every row (O(n)). With a B-Tree index, search is O(log n).

Types of Indexes

  • Primary Index: Automatically created on the PRIMARY KEY column
  • Secondary / Non-Clustered Index: Manually created on any column; index and data are stored separately
  • Clustered Index: Table rows are physically sorted in the order of this index (only one per table)
  • Unique Index: Ensures all indexed values are distinct — also acts as a constraint
  • Composite Index: Built on two or more columns together — useful for multi-column WHERE clauses
  • Full-Text Index: Optimized for text searches using MATCH / AGAINST

Advantages vs. Trade-offs

  • ✅ Massively speeds up SELECT, WHERE, JOIN, ORDER BY operations
  • ✅ Can enforce UNIQUE constraints automatically
  • ❌ Slows INSERT, UPDATE, DELETE (the index must also be updated)
  • ❌ Consumes additional disk space
  • ❌ Low-cardinality columns (e.g., gender with only M/F) benefit little from indexing

B-Tree: How Index Search Works

A B-Tree (Balanced Tree) keeps all values sorted. Searching follows the path: Root → Intermediate Nodes → Leaf Node → Row Pointer. For a table with 1,000,000 rows, a linear scan may take 1,000,000 comparisons. A B-Tree index takes only about 20 comparisons (log₂ 1,000,000 ≈ 20).

Create & Drop Indexes

-- Basic index on a frequently searched column
CREATE INDEX idx_name ON Students (name);

-- Unique index (also enforces uniqueness)
CREATE UNIQUE INDEX idx_email ON Students (email);

-- Composite index (covers queries on both columns)
CREATE INDEX idx_dept_age ON Students (dept, age);

-- Remove an index
DROP INDEX idx_name ON Students;

When Index IS and IS NOT Used

-- ✅ Index USED — exact equality on indexed column
SELECT * FROM Students WHERE email = 'alice@mail.com';

-- ✅ Index USED — range query on indexed column
SELECT * FROM Students WHERE age BETWEEN 18 AND 25;

-- ❌ Index NOT USED — leading wildcard prevents index scan
SELECT * FROM Students WHERE name LIKE '%lice';

-- ❌ Index NOT USED — function on column disables index
SELECT * FROM Students WHERE UPPER(name) = 'ALICE';

-- Check query execution plan
EXPLAIN SELECT * FROM Students WHERE name = 'Alice';

Relationship Types Explained

  • 1:1 (One-to-One): Each student has exactly one ID card; each ID card belongs to exactly one student
  • 1:N (One-to-Many): One department has many students; each student belongs to only one department
  • M:N (Many-to-Many): Many students enroll in many courses, and each course has many students — resolved using the ENROLLMENT junction/bridge table

ER Diagram Symbols

  • Rectangle — Entity (table)
  • Ellipse / Oval — Attribute (column)
  • Diamond — Relationship between entities
  • Underlined attribute — Primary Key
  • Double ellipse — Multi-valued attribute
  • Dashed ellipse — Derived attribute

What is a SQL JOIN?

A JOIN combines rows from two or more tables based on a related column (usually PK = FK). Without JOINs, data split across normalized tables would be impossible to query together efficiently.

Types of JOINs

  • INNER JOIN: Returns only rows where there is a match in BOTH tables
  • LEFT JOIN: Returns ALL rows from the left table; NULL fills unmatched right-side columns
  • RIGHT JOIN: Returns ALL rows from the right table; NULL fills unmatched left-side columns
  • FULL OUTER JOIN: Returns all rows from both tables; NULL fills both sides where no match
  • CROSS JOIN: Cartesian product — every row of left × every row of right (no ON condition)
  • SELF JOIN: A table joined with itself — used for hierarchical data like employee → manager

JOIN SQL Syntax

-- INNER JOIN: only students who have a department
SELECT s.name, d.dept_name
FROM Students s
INNER JOIN Department d ON s.dept_id = d.dept_id;

-- LEFT JOIN: ALL students (NULL if no dept assigned)
SELECT s.name, d.dept_name
FROM Students s
LEFT JOIN Department d ON s.dept_id = d.dept_id;

-- 3-Table JOIN: student → enrollment → course
SELECT s.name, c.course_name, e.grade
FROM      Students   s
JOIN      Enrollment e ON s.student_id = e.student_id
JOIN      Course     c ON e.course_id  = c.course_id;
